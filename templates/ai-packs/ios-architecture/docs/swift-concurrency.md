# Swift Concurrency

Isolation, `Sendable`, cancellation and task rules for each layer of a generated project (Swift 6 language mode, complete strict concurrency). SwiftData specifics are in `swiftdata.md`.

## Isolation depends on the build settings

Where a UseCase or a Repository runs is decided by two build settings, not by the folder it lives in. Generated targets set `SWIFT_STRICT_CONCURRENCY = complete` and `SWIFT_VERSION` (6.0 by default) and set neither `SWIFT_DEFAULT_ACTOR_ISOLATION` nor `SWIFT_APPROACHABLE_CONCURRENCY`: that is mode 1, the one this document describes. Projects created with Xcode's own template enable modes 2 and 3 together, and either setting can be switched on later (Xcode shows them as "Approachable Concurrency" and "Default Actor Isolation"), so check the target's settings before applying the rest.

| | 1. Neither setting (generated by anvil) | 2. `SWIFT_APPROACHABLE_CONCURRENCY = YES` | 3. `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` |
|---|---|---|---|
| A type with no annotation is | nonisolated | nonisolated | `@MainActor`, UseCases, Repositories, DataSources and mappers included |
| `async` method of a UseCase or Repository, awaited from a ViewModel | leaves the main actor and runs on the global concurrent executor | stays on the caller's actor, here the main actor | runs on the main actor, because its type is `@MainActor` |
| Synchronous method (a mapper) | runs wherever it is called | runs wherever it is called | `@MainActor`: code off the main actor cannot call it |
| To take work off the main actor | nothing to add | mark the function `@concurrent` | mark the function `@concurrent` |
| What you must annotate | the `@MainActor` types listed below | the same | also `nonisolated` on what `@concurrent` code touches: DTOs, DTOMappers, hand-written inits and methods of Domain types |
| Test suite of a UseCase, Repository or mapper | no `@MainActor` | no `@MainActor` | MainActor-isolated, because its SUT is (`testing.md` has the rule) |

- The two settings are independent. With mode 3 alone, a function explicitly marked `nonisolated async` still leaves the caller's actor; with modes 2 and 3 together it stays on it. `@concurrent` behaves the same in every mode, so it is the only spelling this document uses for "must not run on the main actor".
- Going from mode 1 to mode 2 can compile without a single diagnostic while the same code starts running on the main actor. Don't change either setting on an existing target without walking through this table again.
- The generated `Core/Networking` value types (`APIError`, `RetryPolicy`, `InterceptorChain`) already carry `nonisolated`, which is redundant in mode 1 and required in mode 3.

## What is `@MainActor`

With no default isolation, isolation is written out. These are `@MainActor`:

- ViewModels (`@MainActor @Observable final class`), Routers (protocol and Impl) and Factories.
- `AppRouter`, `AppRouterImpl`, `AppNavigationCoordinator`, `NetworkMonitor` and `NetworkMonitorImpl`.
- `SwiftDataStack` and `PersistenceAssembly`, when the project has SwiftData.
- Views, through SwiftUI's `View` protocol: don't annotate them.
- In tests, Router mocks and the suites whose SUT is one of the types above (`testing.md`).

Everything else is nonisolated: UseCases, Repositories, DataSources, DTOMappers and DecoratorMappers are stateless `struct`s behind `Sendable` protocols. A DecoratorMapper runs on the main actor only because the ViewModel calls it synchronously, not because it is isolated.

## `Sendable` by layer

| Type | `Sendable` | How |
|---|---|---|
| Domain models, DTOs, Decorators, `DomainError`, `APIError` | Required, declared | `struct` or `enum` whose members are all `Sendable` |
| UseCase, Repository, DataSource and mapper protocols, `APIClient`, `RequestInterceptor` | Required, declared on the protocol | The Impl is a `struct` of `let` dependencies, so it conforms with no extra work |
| Router protocols, `AppRouter` | Declared on the `@MainActor` protocol | Makes `any ArticleRouter` `Sendable` as well |
| ViewModels, Factories, coordinators | Implicit | A `@MainActor` type is implicitly `Sendable`: don't declare it and never add `@unchecked` |
| SwiftData `@Model` objects, `ModelContext` | Never | Not `Sendable` by design (`swiftdata.md`) |

### `@unchecked Sendable` and `nonisolated(unsafe)`

Both switch the checker off without adding any protection, so a data race behind them compiles.

- **Document the invariant.** Allowed only with a doc comment on the declaration that says what makes the type safe and what would break it. The generated cases are `SSLPinningDelegate` and `APIClientImpl`: `final class`es whose stored properties are all `let` (`networking.md` spells out the invariant). Before adding a `var` to one of them, move that state into an `actor` or a `Mutex`.
- **Declared exception: test mocks.** `final class <Feature><Type>Mock: <Protocol>, @unchecked Sendable`, with mutable stubs and counters and no comment. The invariant is the test convention itself: each test owns its mocks, configures them before the call and reads them after it, and the SUT calls them one at a time. If the SUT calls a mock in parallel (`async let`, task group), make that mock an `actor` or guard its state with `Mutex` (`Synchronization`, iOS 18+). Details in `testing.md`.
- **`nonisolated(unsafe)`** has no use in generated code. A shared constant is a `let` of a `Sendable` type, as `private nonisolated static let logger` in `AppNavigationCoordinator`.

## Choosing isolation for new code

| Situation | Use | Why |
|---|---|---|
| UI state, navigation, anything a View reads | `@MainActor` | It has to be on the main thread |
| Stateless logic whose caller decides where it runs (UseCase, Repository, DataSource, mapper) | nonisolated `Sendable` struct | No state to protect; where its `async` methods run depends on the mode |
| Work that must never run on the main actor (decoding a large payload, file I/O, hashing) | `@concurrent` on an `async` function | Always runs on the global concurrent executor, in every mode |
| Mutable state shared between tasks (in-memory cache, SwiftData repository) | `actor` | Serializes access; callers `await` |

- **`@concurrent` lives in Data, never in ViewModels.** A ViewModel awaits a UseCase; the DataSource or Repository that owns the heavy work decides where it runs, so the decision is made once and every caller gets it.
- It needs the Swift 6.2 compiler or later: a toolchain requirement, not a deployment-target one.
- In mode 1 it is redundant on a nonisolated function. Write it anyway on work that must stay off the main actor: the guarantee then survives a change of build settings.
- Add it when profiling shows the main thread blocked, not by default: an `await` on the network already suspends without blocking.

```swift
// Data/Article/DataSources/ArticleFileDataSource.swift (excerpt)
struct ArticleFileDataSourceImpl: ArticleFileDataSource {
    private let fileURL: URL

    func load() async throws -> [ArticleDTO] {
        try await Self.decode(at: fileURL)
    }

    @concurrent
    private static func decode(at fileURL: URL) async throws -> [ArticleDTO] {
        let data = try Data(contentsOf: fileURL)
        return try JSONDecoder().decode([ArticleDTO].self, from: data)
    }
}
```

**Domain models and DTOs** rely on the synthesized memberwise `init`, which nonisolated code can call in every mode, mode 3 included: no hand-written `nonisolated init` is needed. A hand-written `init` or method on a Domain type is `@MainActor` in mode 3 and does need `nonisolated` when Data calls it off the main actor.

## Cancellation

- **Cancellation is not an error.** A cancelled load means nobody is waiting for the result: restore the state the screen had and show nothing.
- **Never `try?` over a cancellable `await`.** `try?` turns `CancellationError` into `nil`, so the caller cannot tell "cancelled" from "no data", carries on, and ends up showing an empty or error state. Use `do`/`catch` with the cancellation branch first.
- **The ViewModel restores the previous state.** `load()` starts with `guard state != .loading`, saves `previousState`, and catches in this order (the whole method is in `new-feature.md`):

```swift
} catch is CancellationError {
    state = previousState
} catch let error as DomainError {
    state = .error(ErrorDecorator.from(error))
} catch {
    state = .error(.generic)
}
```

Without the first branch a cancelled reload would leave the screen in `.loading`, or replace loaded content with an error.

Cancellation reaches the ViewModel as `CancellationError` through every layer:

- `APIClientImpl` turns `URLError.cancelled` into `CancellationError` only when `Task.isCancelled` is true. Any other `URLError.cancelled` (a rejected authentication challenge, an invalidated session) stays `APIError.networkError`, so a real failure is not hidden.
- `RetryInterceptor` calls `Task.checkCancellation()` before the first attempt, never retries a `CancellationError`, and its backoff `Task.sleep` throws when the task is cancelled.
- `DomainError.catching` runs in the caller's isolation (`#isolation`), rethrows `CancellationError`, and treats any failure that arrives after the task was cancelled as cancellation. A Repository that catches errors by hand must rethrow `CancellationError` before mapping anything.

## Tasks

- **Structured first.** `.task { }` for the first load (SwiftUI cancels it when the view goes away), `.task(id:)` when a value drives the work, `async let` or a task group for parallel work inside a UseCase or Repository: all of them propagate cancellation and errors. View-side rules are in `swiftui-code-style.md`.
- **Unstructured `Task { }` only to bridge synchronous code into `async`:** a button action, a debounce. It inherits the actor it is created on and is not cancelled when its creator goes away. If it can outlive the action, store it, cancel the previous one, capture `[weak self]` and return on cancellation, as `AppNavigationCoordinator` does:

```swift
func saveNavigationStateDebounced(persist: @escaping @MainActor (Data) -> Void) {
    saveTask?.cancel()
    saveTask = Task { [weak self] in
        do {
            try await Task.sleep(for: .milliseconds(300))
        } catch {
            return
        }
        guard !Task.isCancelled, let data = self?.encodeNavigationState() else { return }
        persist(data)
    }
}
```

- **Background work started from the main actor:** call a `@concurrent` function or, when there is no function to mark, use `Task { @concurrent in ... }`, which keeps the caller's priority and task-local values. `Task.detached` drops both: use it only when dropping them is the point. In either case pass `Sendable` values in and `await` the result back; don't capture a `@MainActor` object to mutate it from there.
- **`MainActor.assumeIsolated`** only inside a `nonisolated` synchronous callback whose API documents delivery on the main thread; anywhere else it traps. Never use it to silence a diagnostic, and never in code that is already `@MainActor` (`UITableViewDelegate` methods are).

## SwiftData

Only when the project was generated with SwiftData: `@Model` objects and `ModelContext` are not `Sendable`, so a Repository is an `actor` conforming to `ModelActor` and only ids and Domain models cross isolation.
The executor, the Factory wiring, where that work really runs in each mode, migrations and tests are in `swiftdata.md`.
