# ARCHITECTURE.md — Clean + MVVM + Router (iOS 18+)

Layers, dependency direction, data and error flow, navigation and dependency injection of a project generated by anvil. File locations: `PROJECT-STRUCTURE.md`. Step-by-step feature code: `new-feature.md`.

## Layers

```text
                 App  (composition root: knows every layer)
                  |
      +-----------+------------+
      v                        v
+---------------------+   +-------------------------------------+
| Features            |   | Data                                |
| View -> ViewModel   |   | RepositoryImpl -> DataSource        |
|   -> FeatureRouter  |   | DTO, DTOMapper, DomainErrorMapping  |
+----------+----------+   +------------------+------------------+
           | uses                            | implements
           v                                 v
+---------------------------------------------------------------+
| Domain: Models, UseCases, Repository protocols, DomainError   |
+---------------------------------------------------------------+

Core (Networking, DesignSystem, Common, Security, Persistence) is shared
infrastructure without feature knowledge; App, Features and Data use it.
```

Layers are folders inside one app target, not modules: the compiler does not enforce the dependency direction, so code review must. Domain depends on nothing, Data and Features depend on Domain, and only a feature's Factory names Data types.

### App (`App/`)

Composition root and app-lifetime concerns, nothing else.

- `Application/AppMain.swift` (`@main`) creates `AppDependencies` and `AppRouterImpl` (plus the `SwiftDataStack` when SwiftData is enabled) and shows `RootNavigationView`. It holds no logic.
- `Config/`: `AppDependencies`, `AppEnvironment`, `EnvironmentConfiguration`, `Xcconfig/`.
- `Navigation/`: `AppRouter`, `AppRouterImpl`, `RootNavigationView`, `AppNavigationCoordinator`. Only this layer touches `AppRouterImpl.path`, parses deep links and persists navigation.

### Core (`Core/`)

Shared infrastructure. It knows no feature.

- `Networking/`: `APIClient` + `APIClientImpl`, `Endpoint` / `APIEndpoint`, `APIError`, interceptors, retry, SSL pinning (`networking.md`).
- `Common/`: `Extensions/` (shared formatters live here), `Models/ErrorDecorator.swift`, `SwiftUI/{Builders,Components,Modifiers}/`.
- `DesignSystem/Tokens/` (`design-system.md`), `Security/KeychainHelper.swift` (`security-privacy.md`) and, only with SwiftData, `Persistence/` (`swiftdata.md`).
- Known deviation: `ErrorDecorator` is a presentation type, but it lives in Core because every feature shares it. Its `from(_:)` is the only place where Core sees a Domain type (`DomainError`).

### Domain (`Domain/<Concept>/`, `Domain/Common/`)

- Models are `Sendable` value types. UseCases are a protocol plus an `Impl` in separate files; they orchestrate repositories and do not catch or map errors. Repository protocols are owned by Domain and implemented in Data. `DomainError` is the single typed error.
- Organized by domain concept, not by screen. `anvil feature` creates one folder per feature; merge folders when several screens share a concept.
- Not allowed: SwiftUI, SwiftData, URLSession, `APIError`, DTOs or any other infrastructure type. Foundation only.

### Data (`Data/<Concept>/`, `Data/Common/`)

- `ArticleRepositoryImpl`, DataSources (Remote, optional Local and Keychain), DTOs, DTOMappers and `Common/DomainErrorMapping.swift`.
- Repositories delegate to DataSources and never call `APIClient` directly: the data source is the seam that tests and UI-test stubs replace. A SwiftData repository receives its own `ModelExecutor` and never uses the main `ModelContext` (`swiftdata.md`).
- Every repository method that can fail wraps its body in `try await DomainError.catching { ... }`.
- Not allowed: SwiftUI or any Presentation type.

### Features (`Features/<Feature>/`)

Presentation only, one folder per screen.

- The View renders state and forwards UI events. The ViewModel holds state and coordinates use cases. The Decorator is the UI model and the DecoratorMapper builds it from the Domain model. The Router expresses navigation intent. The Factory builds the screen's object graph.
- A feature does not use Data types (DTOs, `RepositoryImpl`, DataSources); only the Factory builds them. Everything shares one target, so nothing but review stops the reference.
- Not allowed in Views and ViewModels: URLSession, DTOs, SwiftData, JSON parsing. The one exception is `@Query` in a View for a read-only list (`swiftdata.md`).

## Data Flow

```text
Data                                  Domain                Presentation
RemoteDataSource -> RepositoryImpl -> UseCase -> ViewModel -> View
ArticleDTO --ArticleDTOMapper--> ArticleModel --ArticleDecoratorMapper--> ArticleDecorator
```

- One DTO type per API response: the DTO is `Codable` and is decoded directly (`networking.md`).
- The repository turns DTOs into models with the DTOMapper; the ViewModel turns models into decorators with the DecoratorMapper. A mapper is a protocol plus an `Impl` in one file, and its method is `map(_:)`.
- Display formatting (dates, numbers, currency) belongs to the DecoratorMapper and uses `.formatted()`, for example `model.publishedAt.formatted(date: .abbreviated, time: .omitted)`. Never create a `DateFormatter` or `NumberFormatter` inline, and never store one in a mapper or a View. A formatter that must be shared is a static instance in `Core/Common/Extensions/` (`new-feature.md`).

## Error Flow

```text
Core / DataSources   APIError (.networkError, .httpError, .decodingError, .invalidURL, .unknown)
                     or the data source's own error
      |  RepositoryImpl: try await DomainError.catching { ... }
      v
Domain               DomainError (.network, .notFound, .unauthorized, .server, .parsing, .unknown)
                     or CancellationError; the UseCase lets it through
      |  ViewModel: ErrorDecorator.from(_:)
      v
Presentation         state = .error(ErrorDecorator), rendered by ErrorView
```

`DomainError` (`Domain/Common/DomainError.swift`; `Error, Sendable, Equatable`) is the only error type that reaches Domain and Presentation. It knows nothing about `APIError`: the translation lives in `Data/Common/DomainErrorMapping.swift`.

```swift
static func catching<T>(isolation: isolated (any Actor)? = #isolation,
                        _ operation: () async throws -> T) async throws -> T {
    do {
        return try await operation()
    } catch is CancellationError {
        throw CancellationError()
    } catch where Task.isCancelled {
        throw CancellationError()
    } catch {
        throw map(error)
    }
}
```

- `catching` runs in the caller's isolation (`#isolation`), so an actor-isolated repository can use its own state inside the closure. It rethrows `CancellationError`, treats a failure that arrives after the task was cancelled as cancellation, and converts the rest with `DomainError.map(_:)`.
- `DomainError.map(_:)` keeps an existing `DomainError`; maps `APIError` (HTTP 401 to `.unauthorized`, 404 to `.notFound`, any other status to `.server`, network and invalid URL to `.network`, decoding to `.parsing`, unknown to `.unknown`); maps a raw `DecodingError` to `.parsing`; and maps anything else to `.unknown`.
- Repositories therefore throw only `DomainError` or `CancellationError`. A repository that catches an error itself rethrows `CancellationError` first.
- Don't turn a load failure into an empty result (`try?`, `?? []`): it later surfaces as an empty or "not found" screen instead of an error the user can retry.
- Don't create per-feature error enums. Add a case to `DomainError` (and to `ErrorDecorator.from(_:)`) only when the UI must react differently.
- `ErrorDecorator` (`Core/Common/Models/ErrorDecorator.swift`) has `title`, `message` and `retryAction: (@Sendable () -> Void)?`. `ErrorDecorator.from(_:)` returns `.network`, `.notFound` or `.server` for those cases and `.generic` for `.parsing`, `.unknown` and `.unauthorized`. All four come with `retryAction: nil`; the View adds the retry.

## ViewModel and View

- The ViewModel is a `@MainActor @Observable final class` with `private(set) var state: ArticleState = .idle`, `private(set) var items: [ArticleDecorator]` and its dependencies injected as protocols (`ArticleUseCase`, `ArticleDecoratorMapper`, `ArticleRouter`). Observation is available from iOS 17; the generator's default deployment target is iOS 18. It does not import SwiftUI.
- State is an enum (`.idle`, `.loading`, `.loaded`, `.error(ErrorDecorator)`); `.idle` renders `Color.clear`. Actions are plain methods, with no Action or Event enums.
- `load()` ignores re-entry while loading and restores the previous state on `CancellationError`: a cancelled load is not a failure.

```swift
func load() async {
    guard state != .loading else { return }

    let previousState = state
    state = .loading

    do {
        let models = try await useCase.execute()
        let decorators = models.map { decoratorMapper.map($0) }
        items = decorators
        state = .loaded
    } catch is CancellationError {
        state = previousState
    } catch let error as DomainError {
        state = .error(ErrorDecorator.from(error))
    } catch {
        state = .error(.generic)
    }
}
```

- The View declares `@State private var viewModel: ArticleViewModel` and assigns it last in `init`. `@State` keeps the first instance while SwiftUI re-creates the View value. Don't add an inline default too: the `init` assignment would be silently discarded.

```swift
init(viewModel: ArticleViewModel) {
    self.viewModel = viewModel
}
```

- Initial load: `.task { await viewModel.load() }`. Use `.task(id:)` only when the id drives the work, as when the selected item's id is both the restart trigger and the query input.
- Retry starts from the action, with no trigger flag: the View copies the `ErrorDecorator` adding `retryAction: { [viewModel] in Task { await viewModel.load() } }`. It captures the ViewModel, not the View, because the closure is `@Sendable`.
- Complete View example and SwiftUI rules: `swiftui-code-style.md`.

## Navigation

| Piece | Location | Role |
| --- | --- | --- |
| `AppRouter` | `App/Navigation/` | `@MainActor` protocol, `Sendable`, with only `push(_ route: some Hashable & Codable)`, `pop()` and `popToRoot()` |
| `AppRouterImpl` | `App/Navigation/` | `@MainActor @Observable final class`; owns `path` (`NavigationPath`) |
| `RootNavigationView` | `App/Navigation/` | The `NavigationStack`, resolver registration, `.onOpenURL`, `@SceneStorage` |
| `AppNavigationCoordinator` | `App/Navigation/` | Deep-link parsing, one-time restore, debounced save |
| `ArticleRouter` | `Features/Article/Navigation/` | Always. Route enum (`Hashable, Codable`), `@MainActor` protocol and `struct` Impl that delegates to `AppRouter`, in one file |
| `ArticleRouteResolver` | `Features/Article/Navigation/` | Optional. `ViewModifier` with `.navigationDestination(for: ArticleRoute.self)` plus `View.withArticleRoutes(appRouter:dependencies:)` |

- ViewModels navigate only through their feature Router protocol and never see `NavigationStack` or `NavigationPath`; tests mock the Router.
- Features never read or replace the whole path: `AppRouter` has no `path`. `pop()` and `popToRoot()` do nothing on an empty path.
- Every route is `Hashable & Codable`, because the path is persisted.
- Add a resolver only when the feature owns destinations. It calls the destination's Factory inside `navigationDestination` and is registered on the root content, in the `body` of `App/Navigation/RootNavigationView.swift`:

```swift
NavigationStack(path: $appRouter.path) {
    ArticleFactory.makeView(appRouter: appRouter, dependencies: dependencies)
        .withArticleRoutes(appRouter: appRouter, dependencies: dependencies)
}
```

The generated root shows a placeholder `Text`; replace it with the first screen's Factory. A detail screen is its own feature (`Features/ArticleDetail/`, with its own Factory) and can share `Domain/Article/` and `Data/Article/` with the list.

### Deep Links and Restoration

- `RootNavigationView` forwards `.onOpenURL` to `coordinator.handleDeepLink(_:)`. Features never handle URLs.
- A link replaces the stack (`appRouter.path = path`); it is never pushed on top of what the user had open.
- A link that arrives before restoration, such as the URL that launched the app, is held and applied right after `restoreNavigationState(from:)`, so it wins over the saved path whichever callback runs first.
- Restoration runs once, from a `.task`, reading `@SceneStorage("app.navigation.path")`; a decode failure is logged and the stack starts empty. Saving is debounced (300 ms) from `.onChange(of: appRouter.path)` and never writes `nil`: if the path cannot be encoded, the last good value stays.
- The generated `navigate(to:)` only logs the host. Add each deep-linkable route there, register the URL scheme (`CFBundleURLTypes`) in Info.plist, and make sure a registered resolver handles the route.

```swift
// App/Navigation/AppNavigationCoordinator.swift
private extension AppNavigationCoordinator {
    func navigate(to url: URL) {
        guard let components = URLComponents(url: url, resolvingAgainstBaseURL: false),
              let host = components.host else {
            Self.logger.warning("Deep link ignored: invalid URL components")
            return
        }

        var path = NavigationPath()
        switch host {
        case "article":
            guard let id = components.queryItems?.first(where: { $0.name == "id" })?.value else { return }
            path.append(ArticleRoute.detail(id: id))
        default:
            Self.logger.debug("Deep link ignored: unknown host \(host, privacy: .public)")
            return
        }
        appRouter.path = path
    }
}
```

### Known Deviation: Router Ownership

The generator creates `AppRouterImpl` in `@main`, and the generated Info.plist sets `UIApplicationSupportsMultipleScenes` to `false`: one window, one router, one coordinator. The reference architecture's ADR-0005 (hierarchical composition roots, as amended) treats the router as window state, not app-lifetime state. Keep the generated shape while the app has a single window.

If you enable multiple scenes, move ownership down: a per-window root view creates its own `AppRouterImpl` and `AppNavigationCoordinator` in `@State`, and `@main` keeps only `AppDependencies`. Never share one `AppRouterImpl` between windows.

### Sheets and Tabs

The generator emits neither.

- A sheet is not a route: `AppRouter` only pushes and pops. Presentation state is UI state, so the presenting View owns it in `@State` (a `Bool`, or an optional `Identifiable` item) and uses `.sheet(isPresented:)` or `.sheet(item:)`. The content comes from the presented feature's Factory, as in a resolver. That closure is re-evaluated when the presenter's state changes, so the cheap-`init` rule in Dependency Injection applies.
- Never push onto the presenting stack from inside a sheet: the pushed screen stays hidden behind the sheet until it is dismissed. Dismiss first, or give the sheet its own `NavigationStack` and `AppRouterImpl` when it needs drill-down.
- `TabView`: one `NavigationStack` per tab, never one stack around the `TabView`, so each tab keeps its own history. `AppRouterImpl` owns a single path, so each tab gets its own `AppRouterImpl` and registers its resolvers on its own stack. The generated root assumes one stack (one coordinator, one `@SceneStorage` key): adding tabs is an App-layer change, not a feature change.

Deeper reference (Axiom plugin, if installed): `axiom-swiftui` (`skills/nav.md`, `skills/architecture.md`).

## App-Level State

The generator creates no app-state type. When the app needs authentication, onboarding or another app-wide flow, model it as one enum (`loading`, `unauthenticated`, `onboarding`, `authenticated`) owned by an `@MainActor @Observable` type in `App/` that the root view switches on. Scattered booleans (`isLoggedIn`, `hasOnboarded`) allow impossible combinations, and the enum keeps that logic out of `@main`. Deeper reference (Axiom plugin, if installed): `axiom-design` (`skills/app-composition.md`).

## Dependency Injection

- Manual constructor injection, with no container, service locator or singleton: the graph is small and statically known, and every lifetime stays visible at its call site.
- `AppDependencies` (`App/Config/AppDependencies.swift`) holds app-lifetime dependencies and is created once in `@main`: the shared `APIClient` and, with SwiftData, the `SwiftDataStack`. Promote a dependency to it only when its lifetime is really app-wide.
- Each feature has one `@MainActor enum ArticleFactory` with `static func makeView(appRouter: AppRouter, dependencies: AppDependencies) -> some View`. Private `make*` helpers build DataSource, DTOMapper, Repository, UseCase, DecoratorMapper, Router and ViewModel, in that order.
- ViewModels receive protocols; only the Factory names concrete types.
- Factory + `@State` cost: SwiftUI can evaluate a `navigationDestination` closure, and therefore the Factory, many times. `@State` keeps the first ViewModel and the rest are built and thrown away, so every `init` reached from a Factory must be cheap: no I/O, no decoding, no network. Put that work in an `async` method called from `.task`.

## Concurrency and Sendable

- Isolation depends on the target's build settings. `swift-concurrency.md` has the table (no default isolation, which is what anvil generates; approachable concurrency; `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`). Read it before assuming where a UseCase or Repository runs.
- What the generated code spells out, whatever the setting: ViewModels, Routers, Factories, `AppRouter`, `AppRouterImpl` and `AppNavigationCoordinator` are `@MainActor`; UseCases, Repositories, DataSources and mappers are stateless `struct`s behind `Sendable` protocols; Domain models, DTOs and Decorators are `Sendable` value types.
- A `@MainActor` type is implicitly `Sendable`, so ViewModels don't declare it.
- `@unchecked Sendable` only for a type that is thread-safe in a way the compiler cannot verify, in practice a `final class` whose stored properties are all `let`; re-check it before adding a `var` (`swift-concurrency.md`; test mocks: `testing.md`).
- Cancellation is never an error: `DomainError.catching` rethrows it, the ViewModel restores the previous state, and `.task` cancels the load when the view goes away.
