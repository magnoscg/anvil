# Swift 6 Concurrency Guide

> Patterns for Swift 6 strict concurrency compliance in Clean Architecture.
> Related skills: `/axiom:audit concurrency`, `axiom:axiom-swift-concurrency`
> Axiom complementa: Actor contention profiling, TaskGroup advanced patterns

## Overview

Swift 6 enforces strict concurrency checking. This guide covers patterns to achieve data-race safety while maintaining Clean Architecture.

### How `Example/` Is Configured

The app and test targets build with Swift 6 language mode and:

| Build setting | Value |
|---------------|-------|
| `SWIFT_DEFAULT_ACTOR_ISOLATION` | `MainActor` |
| `SWIFT_APPROACHABLE_CONCURRENCY` | `YES` |

Consequences:
- Every declaration without explicit isolation is `@MainActor`: Views, ViewModels, Routers, Factories **and also UseCases, Repositories and DataSources**. Placing a type in `Domain/` or `Data/` does not move its work off the main actor.
- Mark `nonisolated` what must be callable from any isolation: DTO `init(from:)`, DTOMapper methods (protocol and Impl), `APIError`, interceptors and `RetryPolicy` in `Core/Networking/`, and `static let logger`.
- Synchronous code called inside a task-group child must be `nonisolated` (this is why DTOMappers are).
- With approachable concurrency, a plain `nonisolated async` function runs on the caller's actor. Work that must leave the main actor (heavy decoding, disk I/O) has to be marked `@concurrent` explicitly.

> Projects generated by `anvil init` do **not** use default MainActor isolation, so some sections below (e.g. "UseCases are not `@MainActor`") apply to them and not to `Example/`.

## Sendable Requirements

### When to Use Sendable

| Type | Sendable? | Reason |
|------|-----------|--------|
| Domain Models | **Required** | Cross actor boundaries |
| DTOs | **Required** | Cross actor boundaries |
| UseCases (struct) | **Required** | Called from different actors |
| Repositories (struct) | **Required** | Called from different actors |
| DataSources (struct) | **Required** | Called from different actors |
| Mappers (protocol) | **Required** | Used across actor boundaries |
| Decorators | **Recommended** | May be passed between actors |
| ViewModels | **NO** | Already @MainActor isolated |
| Views | **NO** | SwiftUI handles isolation |

In `Example/`, the UseCase, Repository, DataSource, Mapper and Router **protocols** declare `: Sendable` explicitly; internal value types (Domain models, most DTOs, Decorators) rely on implicit `Sendable` inference.

### CancellationError Rule

> **NEVER** silence `CancellationError` with `try?` — always propagate it so downstream tasks cancel properly.

Where cancellation is handled in `Example/`:
- `APIClientImpl` turns `URLError.cancelled` into `CancellationError` only when `Task.isCancelled` (a rejected pinning challenge also reports `.cancelled` and must stay an error), and rethrows the `CancellationError` of the retry backoff unchanged.
- `DomainError.catching` runs in the caller's isolation, rethrows `CancellationError`, and treats any failure after cancellation as cancellation; repositories that catch errors themselves (the optional species request in `PokemonDetailRepositoryImpl`, the task-group children in `PokemonListRepositoryImpl`) rethrow it first.
- ViewModels restore the previous state on cancellation instead of showing an error.

```swift
// ❌ WRONG: Swallows cancellation
let result = try? await useCase.execute()

// ✅ CORRECT: Propagate cancellation
let previousState = state
state = .loading

do {
    let result = try await useCase.execute()
    state = .loaded(decoratorMapper.mapToSections(result))
} catch is CancellationError {
    state = previousState
} catch let error as DomainError {
    state = .error(ErrorDecorator.from(error))
} catch {
    state = .error(.generic)
}
```

### Making Types Sendable

```swift
// MARK: - Domain Model (Sendable by default if all properties are Sendable)

struct FeatureModel: Sendable, Equatable, Identifiable {
    let id: String
    let title: String
    let body: String
    let category: Category

    enum Category: String, Sendable, CaseIterable {
        case news, tutorial, review
    }
}

// MARK: - Protocol with Sendable

protocol FeatureUseCase: Sendable {
    func execute() async throws -> [FeatureModel]
}

protocol FeatureRepository: Sendable {
    func fetchFeatures() async throws -> [FeatureModel]
}

protocol FeatureDTOMapper: Sendable {
    func mapToDomain(_ dto: FeatureDTO) -> FeatureModel
}
```

### @unchecked Sendable (Use Sparingly)

Use only when you have thread-safe code that the compiler cannot verify:

```swift
// Core/Networking/Security/SSLPinningDelegate.swift (excerpt)
final class SSLPinningDelegate: NSObject, URLSessionDelegate, @unchecked Sendable {
    // MARK: - Properties

    private let pinnedPublicKeyHashes: Set<String>
    private let pinnedHosts: Set<String>
    private let isEnabled: Bool

    // MARK: - Init

    init(publicKeyHashes: [String], pinnedHosts: Set<String>, isEnabled: Bool = true) {
        self.pinnedPublicKeyHashes = Set(publicKeyHashes)
        self.pinnedHosts = Set(pinnedHosts.map { $0.lowercased() })
        self.isEnabled = isEnabled
        super.init()
    }
}
```

It is safe because every stored property is an immutable `let`. Don't add `var` properties without re-analyzing thread safety (`APIClientImpl` follows the same rule).

## Actor Isolation

### @MainActor for ViewModels

ViewModels are always `@MainActor` because they update UI state:

```swift
@MainActor
@Observable
final class FeatureViewModel {
    private(set) var state: FeatureState = .idle

    private let useCase: FeatureUseCase

    func loadFeatures() async {
        state = .loading
        do {
            let models = try await useCase.execute()
            state = .loaded(models)
        } catch let error as DomainError {
            state = .error(ErrorDecorator.from(error))
        } catch {
            state = .error(.generic)
        }
    }
}
```

### UseCases and Repositories

In `Example/`, UseCases, Repositories and DataSources are **`@MainActor` by default** (default actor isolation). Their `async` methods start on the main actor and only leave it when they `await` something that runs elsewhere: `URLSession` inside `APIClientImpl`, or an explicitly `@concurrent` function. Keep their synchronous work light, and move heavy work into a `@concurrent` function (see `ArchitectureDetailJSONDataSourceImpl` below).

In a project without default MainActor isolation (e.g. generated by `anvil init`), they are not `@MainActor` and run in the caller's context.

### Mapper Isolation Rules

Different mappers have different isolation needs:

| Mapper Type | Location | Isolation | Reason |
|-------------|----------|-----------|--------|
| **DecoratorMapper** | `Features/.../Presentation/Mappers/` | `@MainActor` (by default isolation) | Called from ViewModels, outputs to Views |
| **DTOMapper** | `Data/.../Mappers/` | `nonisolated` methods | Called from Repositories, including task-group children |
| **SDModelMapper** (only with the optional SwiftData stack, not in `Example/`) | `Data/.../Mappers/` | `nonisolated` | Called from a background `ModelExecutor` |

#### DecoratorMapper (@MainActor)

DecoratorMappers transform Domain models to UI Decorators. They:
- Are called from ViewModels (already @MainActor)
- Output Decorators used in Views (@MainActor)
- Perform no heavy computation (<16ms)

In `Example/`, the protocol is declared `: Sendable` with no explicit attribute; default isolation makes it `@MainActor`. In a project without default isolation, write `@MainActor` explicitly:

```swift
// MARK: - FeatureDecoratorMapper

protocol FeatureDecoratorMapper: Sendable {
    func map(_ model: FeatureModel) -> FeatureItemDecorator
}

// MARK: - FeatureDecoratorMapperImpl

struct FeatureDecoratorMapperImpl: FeatureDecoratorMapper {
    func map(_ model: FeatureModel) -> FeatureItemDecorator {
        FeatureItemDecorator(id: model.id, title: model.title)
    }
}
```

> **Note**: `@MainActor` types are implicitly `Sendable` — the actor protects their state.

#### DTOMapper (nonisolated)

Data layer mappers must be `nonisolated` because:
- Repositories call them inside task-group children (`PokemonListRepositoryImpl.fetchDetailsInParallel`), which are not isolated to the main actor; synchronous code called there must be `nonisolated`.
- With the optional SwiftData stack, an SDModel mapper is called from a background `ModelExecutor` for the same reason.

```swift
protocol FeatureDTOMapper: Sendable {
    nonisolated func mapToDomain(_ dto: FeatureDTO) -> FeatureModel
}

struct FeatureDTOMapperImpl: FeatureDTOMapper {
    nonisolated func mapToDomain(_ dto: FeatureDTO) -> FeatureModel {
        FeatureModel(id: dto.id, name: dto.name)
    }
}
```

Private helpers in the Impl are `private nonisolated func` too (see `PokemonListDTOMapperImpl`).

## Background Work with @concurrent (Swift 6.2+)

> Requires the Swift 6.2 compiler (Xcode 26). `Example/` uses it with an iOS 18.0 deployment target.

Use `@concurrent` to force a function to always run on the background thread pool. With default MainActor isolation and approachable concurrency, a `nonisolated async` function runs on the caller's actor, so `@concurrent` is the explicit way to leave the main actor for heavy decoding, disk I/O or CPU-intensive work.

### Example in `Example/`

`ArchitectureDetailJSONDataSourceImpl` keeps its `init` free of I/O (Factories can run many times) and reads + decodes the bundled JSON off the main actor:

```swift
// Data/ArchitectureDetail/DataSources/ArchitectureDetailJSONDataSourceImpl.swift (excerpt)
func loadFeatureDetails() async throws -> [ArchitectureDetailDTO] {
    guard let fileURL else {
        throw DataSourceError.fileNotFound("\(Constants.fileName).\(Constants.fileExtension)")
    }
    return try await Self.decodeFeatures(at: fileURL)
}

// MARK: - Private Methods

private extension ArchitectureDetailJSONDataSourceImpl {
    @concurrent
    nonisolated static func decodeFeatures(at fileURL: URL) async throws -> [ArchitectureDetailDTO] {
        let data = try Data(contentsOf: fileURL)
        return try JSONDecoder().decode(ArchitectureDetailResponseDTO.self, from: data).features
    }
}
```

The DTOs it decodes are `nonisolated struct ...: Codable, Sendable`, so they can be decoded there and returned to the caller.

### When to Use

| Situation | Attribute | Reason |
|-----------|-----------|--------|
| CPU-intensive work (image decoding, parsing, encryption) | `@concurrent` | Always offload to background |
| Library/general-purpose API (caller decides) | `nonisolated` | Runs on caller's actor |
| UI code | `@MainActor` | Must stay on main thread |
| State management with shared data | `actor` | Protects concurrent access |

Keep `@concurrent` work in the Data layer (DataSources), never in ViewModels: ViewModels call UseCases, and the DataSource decides where its heavy work runs.

### Build Settings (Xcode 26+)

| Setting | Value in `Example/` | Purpose |
|---------|---------------------|---------|
| Swift Language Version (`SWIFT_VERSION`) | 6.0 | Strict concurrency checking is complete in Swift 6 mode |
| Default Actor Isolation (`SWIFT_DEFAULT_ACTOR_ISOLATION`) | MainActor | All code @MainActor by default |
| Approachable Concurrency (`SWIFT_APPROACHABLE_CONCURRENCY`) | YES | `nonisolated async` runs on the caller's actor; `@concurrent` to leave it |

> **Philosophy (WWDC 2025-268)**: Start single-threaded. Add async/await for latency. Add @concurrent only when profiling proves CPU work blocks UI. Add actors only when main actor has too much state.

### nonisolated Members on Domain Types

A custom initializer or method on a Domain type that `nonisolated` Data-layer code calls must itself be `nonisolated`. Example: `PokemonType.init(from:)` is called from the DTOMappers' `nonisolated` methods:

```swift
// Domain/Pokemon/Models/PokemonType.swift (excerpt)
nonisolated init(from string: String) {
    self = PokemonType(rawValue: string.lowercased()) ?? .unknown
}
```

The DTOMappers in `Example/` call the synthesized memberwise initializers of Domain models (`PokemonSummaryModel`, `PokemonDetailModel`) from their `nonisolated` methods without extra annotations on the models.

### Custom Actors for Shared State

When you need shared mutable state, use an actor:

```swift
actor FeatureCache {
    private var cache: [String: FeatureModel] = [:]

    func get(_ id: String) -> FeatureModel? {
        cache[id]
    }

    func set(_ feature: FeatureModel) {
        cache[feature.id] = feature
    }

    func clear() {
        cache.removeAll()
    }
}
```

## @preconcurrency for Legacy APIs

Use `@preconcurrency` when importing modules that haven't adopted Sendable:

```swift
// Suppress warnings for legacy module
@preconcurrency import SomeLegacyFramework

// Or for specific protocol conformance
class LegacyDelegate: @preconcurrency SomeLegacyProtocol {
    // ...
}
```

## assumeIsolated Pattern

Use `MainActor.assumeIsolated` when you know code runs on MainActor but compiler doesn't:

```swift
// Example: UIKit callback that we know runs on main thread
func tableView(_ tableView: UITableView, didSelectRowAt indexPath: IndexPath) {
    MainActor.assumeIsolated {
        viewModel.selectItem(at: indexPath.row)
    }
}
```

**Warning**: Only use when you are 100% certain of the execution context. Crashes if wrong.

## SwiftData Concurrency

> `Example/` does not use SwiftData. This section applies only if a project adds the optional SwiftData stack (see `swiftdata.md`).

### The Golden Rule

> **NEVER pass SwiftData models between actors. Pass IDs instead.**

SwiftData models are bound to their `ModelContext` and are NOT thread-safe.

### Wrong vs Right

```swift
// WRONG: Passing model across actors
@MainActor
class FeatureViewModel {
    func saveFeature(_ feature: FeatureSDModel) async {
        await repository.save(feature)  // CRASH RISK
    }
}

// RIGHT: Pass ID, fetch on target context
@MainActor
class FeatureViewModel {
    func saveFeature(_ featureId: UUID) async {
        await repository.save(featureId: featureId)
    }
}
```

### ModelExecutor for Background Operations

`ModelExecutor` only exposes `modelContext` (there is no `perform { }`). The repository is an `actor` conforming to `ModelActor` with the injected executor and container; it runs on that executor and maps to Domain models before returning. This is what `@ModelActor` generates (see `swiftdata.md`).

```swift
// MARK: - FeatureRepositoryImpl

actor FeatureRepositoryImpl: FeatureRepository, ModelActor {
    // MARK: - Properties

    nonisolated let modelExecutor: any ModelExecutor
    nonisolated let modelContainer: ModelContainer

    // MARK: - Init

    init(modelExecutor: any ModelExecutor, modelContainer: ModelContainer) {
        self.modelExecutor = modelExecutor
        self.modelContainer = modelContainer
    }

    // MARK: - FeatureRepository

    func fetchFeature(id: UUID) async throws -> FeatureModel? {
        try await DomainError.catching {
            let descriptor = FetchDescriptor<FeatureSDModel>(
                predicate: #Predicate { $0.id == id }
            )
            return try modelContext.fetch(descriptor).first?.toDomain()
        }
    }
}
```

## Task Management

### Task Cancellation

Always handle cancellation properly: restore the previous state so the screen never stays stuck in `.loading`.

```swift
func loadFeatures() async {
    guard state != .loading else { return }

    let previousState = state
    state = .loading

    do {
        let features = try await useCase.execute()
        state = .loaded(features)
    } catch is CancellationError {
        state = previousState
    } catch let error as DomainError {
        state = .error(ErrorDecorator.from(error))
    } catch {
        state = .error(.generic)
    }
}
```

### Structured Concurrency in Views

Use `.task(id:)` for automatic cancellation:

```swift
struct FeatureView: View {
    @State private var viewModel: FeatureViewModel

    var body: some View {
        content
            .task(id: viewModel.featureId) {
                await viewModel.loadFeature()
            }
    }
}
```

### Unstructured Tasks (When Needed)

Store and cancel manually when you need unstructured concurrency. `AppNavigationCoordinator.saveNavigationStateDebounced(persist:)` uses this pattern for its 300 ms debounce:

```swift
@MainActor
@Observable
final class SearchViewModel {
    // MARK: - Properties

    private var searchTask: Task<Void, Never>?

    // MARK: - Public Methods

    func search(_ query: String) {
        searchTask?.cancel()
        searchTask = Task { [weak self] in
            do {
                try await Task.sleep(for: .milliseconds(300))
            } catch {
                return
            }
            guard !Task.isCancelled else { return }
            await self?.performSearch(query)
        }
    }
}
```

## Common Anti-Patterns

### DON'T: Capture self in detached tasks without isolation

```swift
// WRONG
Task.detached {
    self.updateState()  // Data race!
}

// RIGHT: Capture values, not self
let value = someValue
Task.detached {
    await processValue(value)
}
```

### DON'T: Access MainActor state from non-isolated context

```swift
// WRONG
func backgroundProcess() async {
    viewModel.state = .loading  // Not isolated to MainActor!
}

// RIGHT: Use MainActor.run
func backgroundProcess() async {
    await MainActor.run {
        viewModel.state = .loading
    }
}
```

### DON'T: Forget Sendable on closure parameters

```swift
// WRONG: Non-Sendable closure crosses actor boundary
func process(completion: @escaping () -> Void) async {
    await someActor.doWork()
    completion()  // Warning!
}

// RIGHT: Mark closure as @Sendable
func process(completion: @escaping @Sendable () -> Void) async {
    await someActor.doWork()
    completion()
}
```

## Quick Reference

| Pattern | When to Use |
|---------|-------------|
| `Sendable` | All types crossing actor boundaries |
| `@MainActor` | ViewModels, UI-related classes (implicit for everything else in `Example/`) |
| `nonisolated` | DTO decoding, DTOMapper methods, `Core/Networking` types, `static let logger` |
| `@concurrent` | Heavy decoding / disk I/O that must leave the main actor |
| `withThrowingTaskGroup` / `async let` | Parallel work (`PokemonListRepositoryImpl` / `PokemonDetailRepositoryImpl`) |
| `actor` | Shared mutable state |
| `@preconcurrency` | Legacy API imports |
| `assumeIsolated` | Known context, compiler unaware |
| `Task.detached` | Truly independent work |
| `.task(id:)` | View-driven async operations |
